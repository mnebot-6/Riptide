[CONTEXTO COMPLETO — PROYECTO RIPTIDE]

Soy desarrollador Android (Kotlin + Jetpack Compose), desarrollador web y tengo experiencia con Kotlin Multiplatform (KMP). Estoy desarrollando una app personal llamada Riptide en mi tiempo libre, partiendo de cero como proyecto propio.

---

CONCEPTO DE LA APP

App de productividad con ecosistema marino que crece con la constancia. La puntuación existe internamente pero nunca se muestra como número. El feedback es siempre emocional: mensajes, crecimiento visual del estanque, sensación de progreso sin métricas explícitas. La constancia construye algo bonito. El abandono lo pausa. Nunca lo destruye.

Inspirado en Forest, pero más profundo y personal — orientado a la sensación, no a los números.

---

STACK TÉCNICO

- Kotlin Multiplatform con Compose Multiplatform (una sola UI para Android e iOS)
- Proyecto generado con el KMP Wizard de JetBrains (kmp.jetbrains.com)
- La estructura no tiene carpeta shared: todo vive en composeApp/src/
- commonMain: lógica de negocio, modelos, repositorios, ViewModels, UI
- androidMain / iosMain: implementaciones específicas de plataforma
- Persistencia: Room (local, offline-first), versión 6
- IDs String (UUID) desde el primer día para facilitar sincronización futura
- Capa repositorio que abstrae el origen de datos (fácil migración a Ktor en v4)
- Patrón MVVM

LÓGICA DE CATEGORÍAS MARINAS (MarineCategoryAssigner)

Redistribución automática al crear/editar/eliminar bloques. Nunca visible al usuario.
1 bloque → 5 cat | 2 → 3+3 | 3 → 2+2+2 | 4 → 2+1+1+1 | 5+ → 1 cada uno
La experiencia acumulada en EcosystemState se mantiene intacta.
Se llama en: DataSeeder, MainViewModel (insert/update/deleteBlockAndReassign).

---

LÓGICA RECURRENTES (RecurringTaskGenerator)

generateUpTo(from: LocalDate, daysAhead: Int = 7): genera instancias DayTask para cada
  RecurringTaskDef activo en los próximos N días si no existen ya.
  Instancias generadas como TaskSchedule.OneTime con sourceTaskId = def.id
Se llama en MainViewModel.init y al crear nueva tarea recurrente.

LÓGICA DE EXPERIENCIA Y NIVELES

EcosystemLevelCalculator (commonMain, object):
  xpForLevel(n): nivel 1=0, nivel 2=100, nivel 3=250, nivel 4=450, nivel 5=700... (+50 XP por nivel)
  levelForXp(xp): nivel actual para un total de XP dado
  xpInCurrentLevel(xp): XP acumulada dentro del nivel actual
  xpForNextLevel(level): XP necesaria para completar el nivel actual
  nightBonus(score, bestStreak):
    — score>=1.0 → +50 XP | score>=0.7 → +25 XP | score>=0.4 → +10 XP
    — bestStreak * 5 XP adicionales
  XP_PER_TASK = 10

EcosystemProcessor (commonMain):
  addXpForTask(categories): List<CreatureSpec>   — 10 XP divididas entre categorías; devuelve desbloqueadas
  addNightBonus(score, bestStreak, categories): List<CreatureSpec>   — bonus dividido; devuelve desbloqueadas
  — si el EcosystemState no existe para esa categoría, lo crea
  — actualiza currentLevel automáticamente con EcosystemLevelCalculator
  — detecta criaturas desbloqueadas comparando oldLevel vs newLevel contra allCreatures[].unlockLevel

Flujo XP:
  Al completar tarea (tiempo real) → toggleTaskCompleted → ecosystemProcessor.addXpForTask
    → si hay nuevas → añade a pendingUnlocks en UiState
  Al procesar resumen nocturno → NightSummaryProcessor.processDay → ecosystemProcessor.addNightBonus
    → si hay nuevas → persiste emojis en DataStore via UserPreferencesRepository

---

FLUJO DE DESBLOQUEO DE CRIATURAS

1. EcosystemProcessor devuelve List<CreatureSpec> recién desbloqueadas
2. Tiempo real: MainViewModel añade a pendingUnlocks en UiState directamente
3. Resumen nocturno: NightSummaryProcessor persiste emojis en DataStore
4. Al arrancar: checkPendingUnlocks() lee DataStore → añade a UiState → limpia DataStore
5. Orden de diálogos al arrancar: pendingSummary primero → pendingUnlocks en cola
6. Diálogo de desbloqueo: emoji + mensaje + campo nombre obligatorio
7. confirmUnlock(spec, nickname): guarda MarineCreature en BD + drop(1) de la cola
8. dismissUnlock(): descarta sin nombre + drop(1)

RESUMEN NOCTURNO

NightSummaryProcessor (commonMain):
  processDay(date, blockNames, blockCategories):
    1. Si ya existe DaySummary para esa fecha → return (idempotente)
    2. Expira tareas PENDING → EXPIRED
    3. Calcula score = completadas / total
    4. Llama blockStreakProcessor.processDay(date, blockIds) → Map<String, Int>
    5. Llama ecosystemProcessor.addNightBonus(score, bestStreak, allCategories) → List<CreatureSpec>
    6. Si hay nuevos unlocks → persiste emojis en DataStore via userPreferencesRepository
    7. buildMessage(score, total, completed, streaks, blockNames)
    8. Guarda DaySummary

  buildMessage: score base + prefijo "X de Y tareas" (si parcial) +
    sufijo " [NombreBloque] lleva N días seguidos 🔥" (si racha top >= 3)

  Mensajes base:
    score == 0.0 → "Las corrientes cambian. Mañana el mar sigue ahí."
    score < 0.4  → "Algo se movió hoy. Eso cuenta."
    score < 0.7  → "Buen empuje hoy."
    score < 1.0  → "El estanque está vivo."
    score == 1.0 → "Hoy el estanque brilló."

NightSummaryWorker (androidMain, WorkManager):
  - CoroutineWorker que construye blockNames + blockCategories y llama processDay(today, ...)
  - Construye userPreferencesRepository para persistir unlocks nocturnos
  - Se planifica como OneTimeWorkRequest con delay hasta la hora configurada
  - ExistingWorkPolicy.REPLACE para reemplazar al cambiar la hora

NightSummaryScheduler (commonMain, interfaz):
  - getNightSummaryTime(): Flow<LocalTime>
  - setNightSummaryTime(time: LocalTime)
  - scheduleWorker(time: LocalTime)
  Implementaciones: androidMain (DataStore + WorkManager), iosMain (stub vacío)

Flujo al arrancar la app (MainActivity.onCreate):
  1. seedIfEmpty (DataSeeder)
  2. Construye blockNames + blockCategories + userPreferencesRepository
  3. Procesa ayer con NightSummaryProcessor (fallback si el worker no ejecutó)
  4. Planifica WorkManager con la hora guardada en DataStore
  5. viewModel.reload() → checkPendingSummary() + checkPendingUnlocks() → diálogos al arrancar

ESTADOS DE TAREA

PENDING: estado por defecto al crear.
COMPLETED: da 10 XP al ecosistema marino (divididas entre categorías del bloque).
EXPIRED: tareas PENDING procesadas en resumen nocturno; no dan experiencia.
POSTPONED: tarea original marcada como pospuesta; se crea nueva instancia PENDING en la nueva fecha.
