Lo que construiste — y qué pasa bajo el capó

Arrancamos desde algo que ya conoces: la app en acción. Luego vemos la maquinaria que lo hace posible.

Riptide en una frase

Riptide es una app de productividad con un giro emocional: en lugar de mostrarte números fríos, te recompensa construyendo un ecosistema marino vivo. Cuanto más constante eres, más criaturas nadan en tu acuario.

La puntuación nunca se muestra como número. El feedback es siempre visual y emocional: criaturas que crecen, fondos que cambian, una lootbox que aparece de sorpresa.

📋
WorkBlocks
Áreas de tu vida (trabajo, salud, ocio). Cada bloque tiene categorías marinas asignadas.
✅
DayTasks
Las tareas del día. Completarlas da XP al ecosistema marino correspondiente.
🐠
Ecosystem
40 especies marinas que desbloqueas y ves crecer. Cada categoría sube de nivel por separado.

El código detrás del checkbox

Esta función vive en MainViewModel.kt y es el corazón de la lógica de completado.

CÓDIGO 
fun toggleTaskCompleted(task: DayTask) {
  viewModelScope.launch {
    if (task.status == TaskStatus.COMPLETED) {
      val summaryExists =
        daySummaryRepository.getByDate(date) != null
      newStatus = if (summaryExists)
        TaskStatus.EXPIRED
      else
        TaskStatus.PENDING
    } else {
      // Completar: dar XP solo si !hasBeenRewarded
    }
  }
}
EN CASTELLANO

toggleTaskCompleted: función que se llama al pulsar el checkbox. Puede marcar O desmarcar.

viewModelScope.launch: "haz esto en segundo plano sin bloquear la pantalla".

if COMPLETED → desmarcar: si ya estaba completada, hay que decidir a qué estado vuelve.

summaryExists: si el resumen nocturno ya procesó ese día, la tarea no vuelve a PENDING — va a EXPIRED (ya pasó).

else → completar: solo da XP si hasBeenRewarded es false. Así completar y descompletar varias veces no multiplica el XP.

02

Los actores: quién hace qué

Tu app tiene 5 capas bien definidas. Cada una tiene un rol, y ninguna hace el trabajo de la otra.

El reparto de Riptide

Piensa en tu app como una cocina de restaurante — no, espera. Piensa en una orquesta: cada sección toca su parte, nadie improvisa fuera de su registro, y el director (el ViewModel) coordina el tempo.

UI · Compose Pantallas y componentes visuales. Solo muestra lo que le dan — no decide nada.
Archivos: MainScreen.kt, AquariumCreature.kt, EcosystemScreen.kt… La UI observa el StateFlow del ViewModel y se redibuja cuando cambia. Nunca escribe datos directamente.
⬍
ViewModel El cerebro. Recibe acciones del usuario y coordina repositorios y procesadores.
Archivo: MainViewModel.kt. Tiene acceso a todos los repositorios y procesadores. Expone un único _uiState: MutableStateFlow<MainUiState> que la UI observa. Es platform-independent — vive en commonMain, no en androidMain.
⬍
Domain / Processors La lógica de negocio pura. EcosystemProcessor, NightSummaryProcessor, LootboxResolver…
Carpeta: domain/. Clases Kotlin puras, sin Android, sin Room. Son las más fáciles de testear (37 tests los cubren). Aquí vive toda la inteligencia: cálculo de XP, detección de lootboxes, rachas.
⬍
Repositories Interfaz de acceso a datos. El ViewModel habla con interfaces — no sabe si hay Room, cloud o memoria.
Las interfaces viven en commonMain/domain/repository/. Las implementaciones reales están en androidMain/data/repository/. Esto permite testear con repositorios fake en memoria, sin tocar la base de datos.
⬍
Room / SQLite La base de datos local. Persiste todo cuando cierras la app. Esquema v10.
Archivo central: RiptideDatabase.kt. 8 tablas, 8 DAOs, migraciones reales (sin nunca usar fallbackToDestructiveMigration — eso borraría los datos del usuario). Los mappers convierten entre entidades de Room y modelos de dominio.

Pulsa cada capa para ver más detalles.

Las migraciones: el historial del esquema

Cada vez que añades un campo nuevo a la base de datos, escribes una migración. Mira cómo se añadió el campo de notificaciones en la versión 10.

CÓDIGO 
val MIGRATION_9_10 = object : Migration(9, 10) {
  override fun migrate(db: SupportSQLiteDatabase) {
    db.execSQL("ALTER TABLE day_tasks
      ADD COLUMN notificationsEnabled
      INTEGER NOT NULL DEFAULT 0")
    db.execSQL("ALTER TABLE recurring_task_defs
      ADD COLUMN notificationsEnabled
      INTEGER NOT NULL DEFAULT 0")
  }
}
EN CASTELLANO

Migration(9, 10): "cuando la app se actualice de versión 9 a 10, ejecuta este código".

execSQL("ALTER TABLE…"): modifica la tabla existente añadiendo una columna nueva — sin tocar los datos existentes.

notificationsEnabled INTEGER NOT NULL DEFAULT 0: el campo nuevo. DEFAULT 0 = todas las filas antiguas empiezan con false (0 en SQLite).

Si no escribieras esta migración, Room lanzaría un error y la app no abriría. Los datos del usuario se perderían. Por eso nunca se usa fallbackToDestructiveMigration.

🏦 Room como un banco de datos inmutable

Room nunca modifica el pasado — solo añade. Si necesitas cambiar una tabla, escribes una migración que describe exactamente qué cambia. Como un libro de contabilidad: no taches, añade una línea nueva.

04

El motor del ecosistema marino

Cómo cada tarea completada se transforma en XP, niveles y criaturas. La joya de la corona de Riptide.

El loop de recompensa

Cada WorkBlock tiene categorías marinas asignadas. Cuando completas una tarea de ese bloque, el XP va a esas categorías. Las categorías suben de nivel. En ciertos niveles, aparece una lootbox con una nueva criatura.

1
Tarea completada → 10 XP
Cada tarea da exactamente XP_PER_TASK = 10 puntos, repartidos equitativamente entre las categorías del bloque. Bloque con 2 categorías → 5 XP cada una.
2
XP → Nivel de categoría
Cada categoría (FISH, CRUSTACEAN, etc.) acumula XP y sube de nivel. La curva escala: nivel 2 cuesta 1 XP, nivel 3 cuesta 20, nivel 6 cuesta 100, nivel 7 cuesta 150…
3
Niveles clave → Lootbox
CATEGORY_UNLOCK_LEVELS define en qué niveles aparece cada lootbox. Al alcanzar uno, se genera un PendingLootbox que espera a que el usuario lo abra.
4
Apertura → Criatura revelada
Al abrir, LootboxResolver.resolve() elige la especie aleatoriamente por peso de rareza entre las aún bloqueadas. La criatura aparece en el acuario.

El overflow de XP: el mecanismo catch-up

Si una categoría ya tiene todas sus criaturas desbloqueadas, el XP no se desperdiciaría — se redistribuye. Como el agua que busca el punto más bajo.

💧 La mecánica del overflow

Cuando una categoría está "completa" (todas sus especies desbloqueadas), el 50% del XP que recibe se desvía a la categoría con menor nivel entre las no-completas. Esto evita que los jugadores avanzados dejen de progresar.

CÓDIGO 
suspend fun addXpForTask(
  categories: List<MarineCategory>
): List<PendingLootbox> {
  val targets = if (categories.isEmpty()) {
    ecosystemStateRepository.getUnlocked()
      .map { it.category }
      .filter { it != MarineCategory.DECORATION }
  } else { categories }
  val xpEach = XP_PER_TASK / targets.size
  return targets.flatMap { addXp(it, xpEach) }
}
EN CASTELLANO

categories.isEmpty(): si la tarea no pertenece a ningún bloque, el XP se reparte entre TODAS las categorías desbloqueadas.

filter DECORATION: la categoría de decoración nunca recibe XP — es solo visual.

xpEach = XP_PER_TASK / targets.size: el XP se divide equitativamente. 10 XP con 2 categorías → 5 XP cada una.

flatMap { addXp }: llama a addXp para cada categoría y junta todas las lootboxes generadas en una sola lista.

05

Cuando algo falla

La intuición de depuración más valiosa: saber en qué capa buscar según el síntoma.

Diagnóstico por síntoma

Antes de pedirle a la IA que arregle un bug, necesitas decirle dónde mirar. Cada síntoma apunta a una capa distinta.

!
"La pantalla no se actualiza" → busca en el ViewModel
La UI solo muestra lo que hay en _uiState. Si no se actualiza, el ViewModel probablemente no llama a _uiState.update { … } tras la operación.
!
"Los datos desaparecen al reabrir" → busca en Room / migración
Si la escritura a Room falla silenciosamente, o si una migración borró datos, los datos no persisten. Revisa los DAOs y el log de Room.
!
"El XP se duplica" → busca hasBeenRewarded
Hay un guard específico para esto. Si el XP se multiplica, alguien está llamando a addXpForTask cuando hasBeenRewarded ya es true.
!
"La criatura no aparece en el acuario" → busca loadDay
El acuario se alimenta de creaturesData en MainUiState. Ese campo se rellena en loadDay(). Si no se llama tras desbloquear, la pantalla no se entera.

El guard que protege el XP

Este patrón aparece en muchos sitios de Riptide: un booleano que actúa como "ya lo hice, no lo repitas". Es como un sello de correos — una vez estampado, no cambia.

CÓDIGO 
data class DayTask(
  val id: String,
  val title: String,
  val status: TaskStatus,
  val hasBeenRewarded: Boolean = false,
  // ...
)

// En toggleTaskCompleted:
if (!task.hasBeenRewarded) {
  ecosystemProcessor.addXpForTask(categories)
  dayTaskRepository.update(
    task.copy(hasBeenRewarded = true)
  )
}
EN CASTELLANO

hasBeenRewarded: Boolean = false: campo en la tarea que empieza a false y solo pasa a true una vez.

if (!task.hasBeenRewarded): "solo da XP si aún no se ha dado". Esto protege contra desmarcar y volver a marcar.

task.copy(hasBeenRewarded = true): crea una copia de la tarea con ese campo activado. Los data classes de Kotlin son inmutables — no se modifican, se copian con cambios.

Una vez que hasBeenRewarded es true, nunca se resetea. El XP es un evento de un único sentido.

🔒 Inmutabilidad como herramienta de debugging

Los data classes inmutables hacen el debugging más fácil. Si algo cambia, hay exactamente un sitio donde ocurrió: en el .copy(). No hay "quién modificó este objeto misteriosamente".

Vista de pájaro de todo el sistema. La arquitectura que tienes ahora te permite construir sobre ella con confianza.

Receta para añadir una feature nueva

La arquitectura te da un recorrido casi automático. Aquí el checklist para cualquier feature que afecte datos.

1
¿Necesita campo nuevo en DB? → Migration
Añade el campo al data class, al Entity, actualiza el Mapper, sube la versión de DB y escribe MIGRATION_N_N+1.
2
¿Necesita lógica nueva? → Processor en domain/
Crea o amplía un processor en domain/. Escribe un test en commonTest con un Fake repository. Sin tocar Room.
3
¿Necesita acción del usuario? → ViewModel
Añade una función en MainViewModel (o el ViewModel correcto). Llama al processor, actualiza _uiState al final.
4
¿Necesita mostrarse? → UI en presentation/
Observa el uiState en la pantalla correspondiente. La UI es reactiva: si _uiState cambia, la pantalla se redibuja automáticamente.

El contrato entre capas: la interfaz de repositorio

Este patrón es el pegamento de toda la arquitectura. La interfaz define qué se puede hacer, sin decir cómo.

CÓDIGO 
// commonMain — define el contrato
interface DayTaskRepository {
  suspend fun getByDate(date: LocalDate): List<DayTask>
  suspend fun insert(task: DayTask)
  suspend fun update(task: DayTask)
  suspend fun delete(id: String)
}

// androidMain — implementación real con Room
class DayTaskRepositoryImpl(
  private val dao: DayTaskDao
) : DayTaskRepository { ... }
EN CASTELLANO

interface: un contrato. "Cualquiera que quiera ser un DayTaskRepository tiene que saber hacer estas cosas".

suspend fun: función que puede pausarse y esperar sin bloquear la app. Todas las operaciones de base de datos son asíncronas.

DayTaskRepositoryImpl: la versión real, que usa el DAO de Room. Solo vive en androidMain — no en el código compartido.

En tests, FakeDayTaskRepository implementa la misma interfaz pero guarda los datos en una lista en memoria. El Processor no nota la diferencia.
